# ADR 0024: 双后端特性分级（L0/L1/L2）与场景热路径 SoA

- 状态: Accepted
- 日期: 2026-08-12
- 关联: STANDARDS §15, ARCHITECTURE §4.5 / §6, PLAN M17/M18；配合 ADR 0020

## 背景

引擎固定 **D3D12 + Vulkan** 双实装，存在能力差与近似翻倍的维护成本。场景侧采用场景树而非全量 ECS，若热路径仍按深树随机访问，大规模绘制会先于「缺 ECS」成为瓶颈。需要可执行的优化约定，而不是口头「以后注意」。

## 决策

1. **特性分级**  
   - **L0**：双后端必须对齐（通用主路径）。  
   - **L1**：可暂单端，须 Feature + 追平计划。  
   - **L2**：允许永久差，须 Feature + 可诊断降级（无假成功）。  
2. **落地顺序**：先 Windows D3D12 正确性，再 Vulkan（Win → Linux）；大特性禁止两端从零并行。  
3. **场景数据**：保留 `World/Node` 为权威；渲染提取为 `RenderScene` 等 **SoA/连续缓冲**；规模优先实例化/间接绘制/GPU Cull。  
4. **全量 ECS 不做默认**；局部表/局部 ECS 仅在有性能证据时经新 ADR 引入。  
5. 操作细则写入 [STANDARDS.md §15](../../STANDARDS.md)。

## 备选方案

- 强制一切 L0 双端同日完成 —— 进度过慢，否决。  
- 一上来全量 ECS —— 与 2D/3D 混合编辑心智冲突，过早，否决。  
- 仅 RHI、不分级 —— 能力差会渗进业务，否决。

## 后果

- 优点：维护成本可控；规模优化有清晰抓手；与「非 ECS」定位一致且可演进。  
- 代价：需维护 Feature 矩阵与分级标注纪律。

## 学习提示

1. L0/L1/L2 是产品契约，不是实现细节。  
2. SoA 提取 ≠ ECS；先把可见列表变连续，再谈架构革命。  
3. 「先 D3D12」是降风险，不是永远偏心某一后端。
