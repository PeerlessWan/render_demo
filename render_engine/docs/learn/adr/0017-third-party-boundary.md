# ADR 0017: 第三方引入边界与强制抽象层

- 状态: Accepted
- 日期: 2026-08-12
- 关联: docs/THIRD_PARTY.md, PLAN 风险锁死

## 背景

引擎范围大，若全部自研会拖垮进度；若业务直接依赖三方头，换库成本会扩散到全仓库，并失去教学上的「接口/实现分离」示范。

## 决策

1. **自研**：RHI、FrameGraph、RenderSystem、Material/变体、主循环、ActionMap、对外 Net/Physics/UI 等 **抽象接口**。  
2. **三方可引入**：物理求解器、ImGui/RmlUi、glTF/图片解码、DXC、Vulkan SDK、网络库、DLSS/FSR、音频辅助、D3D12MA/VMA 等（清单见 THIRD_PARTY）。  
3. **平台能力**：视频硬解随后端、WASAPI/GameInput、X11/Wayland 等按需，仍经引擎媒体/平台/输入适配。  
4. **强制抽象层（无一例外）**：  
   - 每个三方对应至少一个引擎接口或适配模块；  
   - 业务 / Sandbox / 其它引擎子系统 **禁止** 直接 `#include` 三方头（学习 Sample 对照章节可例外并标明）；  
   - 替换三方以改适配层 + 构建为原则，上层调用保持稳定。  
5. 清单、对照表与许可维护在 [THIRD_PARTY.md](../../THIRD_PARTY.md)。

## 备选方案

- 业务直接依赖三方 —— 集成快，换库与教学成本高，否决。  
- 仅对「大」库做抽象 —— 边界模糊，小库仍会泄漏，否决。

## 后果

- 优点：可替换、可测、教学清晰。  
- 代价：多一层样板代码；接口设计需克制（不过度抽象）。

## 学习提示

1. 先会用 `I*`，再打开三方文档。  
2. 换 Jolt/ImGui/httplib 不应迫使改玩法或 Sandbox 业务逻辑。  
3. 「薄封装」≠「透传所有三方类型」——公开 API 用引擎类型。
